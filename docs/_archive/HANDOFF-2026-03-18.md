## Why We're Starting Fresh

### The Original Architecture (v2)
CarabinerOS v2 was a Turborepo monorepo with three layers:
- **Next.js 15 frontend** (`apps/web/`) — custom React UI
- **FastAPI wrapper** (`engine/main.py` + `engine/bridge.py`) — Socket.IO bridge to Agent Zero
- **Agent Zero submodule** (`engine/agent-zero/`) — AI agent framework

### The Problem
The wrapper architecture (`bridge.py` → `main.py` → Agent Zero) created a chain of abstraction that broke communication:

1. **litellm async hang:** Agent Zero uses litellm for LLM calls. When called through our FastAPI/uvicorn event loop via `bridge.py`, litellm's `acompletion()` with the `ollama` provider hangs indefinitely. Direct calls to Ollama work fine. The `ollama_chat` provider works in isolation but not through the full wrapper chain.

2. **Double Socket.IO layer:** We reimplemented Socket.IO on top of Agent Zero's already-working websocket layer. Our `main.py` polled Agent Zero's internal logs and re-emitted them as our own events — essentially rebuilding what Agent Zero already does natively.

3. **Response cleaning symptoms:** We built an entire response cleaning pipeline to strip Agent Zero artifacts ("Agent 0", "subordinate", tool names) because the wrapper exposed internal state that Agent Zero's own UI handles internally.

**Esteban's insight:** "It's like trying to run a restaurant with an airfryer when I already have an industrial fryer that can do exactly the same." Agent Zero has a working chat UI, streaming, agent delegation, and tool system. Wrapping it adds complexity and breaks things.

### The Decision
- **Use Agent Zero as the backend engine directly** (no bridge.py, no main.py wrapper)
- **Build a React/Next.js frontend** that speaks Agent Zero's native websocket protocol
- **Keep the overlay pattern** for tools, extensions, and profiles (this works perfectly)
- **Keep all database/domain code** (models, migrations, seed data, business logic)

```
├── carabiner/             # CarabinerOS domain layer
│   ├── api/               # REST endpoints (workspace CRUD)
│   ├── domain/            # Business logic (connectors, reporting, protocols)
│   └── db/                # SQLAlchemy models + Alembic migrations
```

**Key difference from v2:** No bridge.py, no main.py wrapper. Agent Zero IS the backend. The Next.js frontend connects to Agent Zero's native websocket (`state_request` events) and REST API directly. The CarabinerOS REST endpoints (workspace CRUD, reporting) mount alongside Agent Zero's Flask routes.

### Agent Zero Native Protocol (what the frontend needs to speak)

**WebSocket (Socket.IO):**
```javascript
// Send message
POST /message_async { prompt, context, attachments[] }

// Receive updates via Socket.IO
socket.emit("state_request", {
  context: "chat-id",
  log_from: lastLogVersion,
  notifications_from: lastNotifVersion,
  timezone: userTimezone
})

// Response shape
{
  context: "chat-id",
  log_version: 42,
  logs: [{ no, type, heading, content, kvps }],
  log_progress: "Running tool...",
  log_progress_active: true,
  contexts: [...],  // chat list
  tasks: [...],
  notifications: [...]
}
```

### LLM Configuration
**IMPORTANT:** Use `ollama_chat` (not `ollama`) as the provider for litellm async compatibility:

```env
A0_SET_chat_model_api_base=http://localhost:11434
```

## Key Lessons Learned

1. **Don't wrap working systems** — Agent Zero's chat pipeline works. Wrapping it in FastAPI/Socket.IO added complexity and bugs.
2. **litellm provider matters** — `ollama` vs `ollama_chat` determines whether async calls work. Always use `ollama_chat`.
3. **Overlay pattern is solid** — Tools, extensions, and profiles in `usr/` work perfectly. This is the right customization mechanism.
4. **The domain code is the real IP** — Tools, profiles, database models, business logic. The UI framework is replaceable.
5. **Start with what works, then customize** — Don't rebuild plumbing. Build on proven infrastructure.
